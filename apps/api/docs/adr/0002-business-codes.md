# ADR 0002: Business codes generated from a counter table

- **Status:** Accepted
- **Date:** 2026-10-02

## Context

Readers, copies, loans, reservations, fines and payments have a human-readable
code shown in the UI next to the internal numeric id. They were generated by
`BEFORE INSERT` triggers that computed `MAX(code) + 1`:

- two concurrent inserts could read the same maximum and collide on the
  `UNIQUE` constraint;
- `generate_loan_code()` parsed the counter from the wrong offset (`'-00001'`
  became `-1`), so the third loan of a day collided with the first and failed
  with 409;
- the application had to `refresh` every entity after saving to read the code;
- the formats were inconsistent (`PRE-YYYYMMDD-NNNNN`, `EJ-YYYY-NNNN`,
  `MULT-YYYY-NNNNN`, ...).

## Decision

- **One format for every series:** `PREFIX-YYYY-NNNNN`, a three-letter prefix,
  the year the counter restarts on, and a five-digit zero-padded counter:
  `LEC` readers, `EJE` copies, `PRE` loans, `RES` reservations, `MUL` fines,
  `PAG` payments. Year-prefixed sequential numbers are the usual convention for
  business documents: sortable, readable, and small after the yearly reset.
- **The format is domain logic, in Java:** each entity declares its
  `CodeSeries`, a pure record that is unit tested.
- **The counter lives in Postgres**, in `code_sequences(series, period,
  last_value)`, incremented with a single atomic upsert:

  ```sql
  INSERT INTO code_sequences (series, period, last_value) VALUES (?, ?, 1)
  ON CONFLICT (series, period) DO UPDATE SET last_value = code_sequences.last_value + 1
  RETURNING last_value
  ```

  The row lock serializes concurrent callers. `CodeGenerator` runs inside the
  caller's transaction (`Propagation.MANDATORY`), so a rollback releases the
  number and the sequence stays gapless.

## Identifiers in URLs

The admin API keeps the numeric `id` in its routes; the code is for people.
Hiding ids does not protect a resource: every request must be authorized on the
server (planned with Spring Security). If a public view is added, it should use
the code or a UUIDv7 in its URLs so internal ids and volumes are not exposed.

## Consequences

- No triggers or code-generation functions remain in the database (V2).
- Existing codes were rewritten to the unified format (V3); this was acceptable
  only because the system had not been released.
- Creations in the same series and year are serialized on one row. That is
  fine for a library's volume; a high-throughput system would trade gaplessness
  for a plain `SEQUENCE`.
